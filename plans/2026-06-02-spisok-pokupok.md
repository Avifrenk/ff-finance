# План: Совместный список покупок

Цель ветки `feat/shopping-list` — добавить общий для пары список «что купить». Сценарий:

- Алина перед походом в магазин быстро накидывает позиции («молоко, хлеб, яйца, корм собаке, ...»).
- Ави открывает PWA в магазине, видит список в реалтайме, отмечает купленное галочкой.
- На главной видно бейдж «🛒 N позиций» — чтобы не забыть проверить перед выходом.

UX-фильтр прежний: жена должна понять интерфейс с первого раза. Один экран, одно поле ввода, чекбоксы. Никаких категорий, лимитов, тегов, приоритетов в MVP.

## Принципы

- **Один общий список на household.** MVP — ровно один список «Покупки» на семью. Несколько списков («Шуферсал», «Рами Леви», «Хозтовары») — отдельная фича `feat/shopping-multilists`, не сейчас. Reasoning: 90% пар обходятся одним списком; второй экран «выбери список» — это уже когнитивная нагрузка, которую жена не оценит.
- **MVP без интеграции с operations.** Купили → галочка → позиция уходит «в купленные». **Не** создаём автоматически expense-операцию. Reasoning: «сколько стоило / с какого счёта / какая категория / как разбить по позициям» — это четыре вопроса на каждый поход в магазин, что убивает UX. Если фича приживётся — отдельной веткой `feat/shopping-to-expense` сделаем кнопку «Создать трату из купленного» с одним числом «общая сумма чека» и одной категорией «Продукты». Пока — пусть это будет просто список.
- **Realtime через Supabase.** Один партнёр добавил позицию — у второго она появилась сразу, без F5. Используем существующий `supabase.channel(...)` (как в Фазах 3-7). Иначе фича теряет смысл: жена пишет, муж в магазине этого не видит.
- **Купленное не удаляется автоматически.** После галочки позиция уходит вниз в секцию «Куплено сегодня» (серым, зачёркнутым). Reasoning: (а) видно, что уже взял в корзину — не путается; (б) если случайно отметил — легко вернуть; (в) на следующий день старое «купленное» автоматически скрывается из основного экрана (но остаётся в БД для возможной будущей аналитики «что покупаем чаще всего»). Полное удаление — отдельным крестиком, идёт через soft delete (`deleted_at`).
- **Безопасное добавление.** Enter / тап ➕ → позиция добавлена, поле очищено, фокус остался. Paste нескольких строк → batch insert (одна строка = одна позиция). Это закрывает кейс «Алина накидывает 15 позиций подряд» без голоса (см. [[feedback-no-voice-input]]).
- **Минимум полей.** В MVP у позиции только `title` (строка) — больше ничего. Никаких `qty`, `unit`, `note`, `priority`. Reasoning: всё что нужно — пишется прямо в title («2 л молока», «хлеб бородинский»). Структурированные поля можно добавить позже, если выяснится, что они реально нужны.
- **Двухуровневая приватность не применима.** Список покупок — по определению семейный. Нет «приватной позиции в списке». Если кто-то хочет купить подарок партнёру втайне — пусть пишет в свои заметки в телефоне, не наша задача.
- **Build + tsc + lint чистые** перед коммитом каждой подфазы.

## Фазы

- [x] **Фаза 1. Миграция: таблица `shopping_items` + RLS + realtime publication.**
  - Миграция `supabase/migrations/20260602100000_shopping_items.sql`:
    - `create table public.shopping_items` со столбцами:
      - `id uuid primary key default gen_random_uuid()`
      - `household_id uuid not null references households(id) on delete cascade`
      - `title text not null check (char_length(trim(title)) between 1 and 200)`
      - `added_by uuid not null references auth.users(id)`
      - `checked_at timestamptz null` — null = «надо купить», not null = «куплено»
      - `checked_by uuid null references auth.users(id)` — кто отметил
      - `deleted_at timestamptz null` — soft delete
      - `created_at timestamptz not null default now()`
    - Индексы:
      - `shopping_items_household_idx` on `(household_id, deleted_at, checked_at, created_at desc)` — основной запрос «активные позиции household'а».
    - RLS:
      - `enable row level security`.
      - Policy `shopping_items_select`: `household_id in (select household_id from members where profile_id = auth.uid())`.
      - Policy `shopping_items_insert`: то же + `added_by = auth.uid()`.
      - Policy `shopping_items_update`: то же (любой член household может отметить/восстановить).
      - Policy `shopping_items_delete` — не нужна, удаление через update `deleted_at = now()`.
    - `alter publication supabase_realtime add table public.shopping_items` — для realtime.
    - GRANTs не нужны: RLS поверх authenticated сама закроет.
  - Применить: `npm run db:push`.
  - `src/types/database.ts`: добавить тип `shopping_items` (Row/Insert/Update).

- [x] **Фаза 2. Хук `useShoppingList`.**
  - `src/hooks/useShoppingList.ts`:
    - Возвращает `{ pending, doneToday, loading, add, addBatch, toggle, remove, restore }`.
    - `pending` — `deleted_at is null && checked_at is null`, sorted by `created_at desc`.
    - `doneToday` — `deleted_at is null && checked_at >= start_of_today_local`, sorted by `checked_at desc`. Граница «сегодня» — по локальному `Date()` пользователя, не UTC.
    - `add(title)` — insert одной позиции, trim, защита от пустой строки.
    - `addBatch(titles)` — insert многих позиций одним запросом (`.insert([...])`), для paste-сценария.
    - `toggle(id)` — если `checked_at` null → `checked_at = now(), checked_by = auth.uid()`; иначе обратно (`checked_at = null, checked_by = null`).
    - `remove(id)` — `deleted_at = now()`.
    - `restore(id)` — `deleted_at = null` (для «отменить удаление», см. Фаза 3).
    - Подписка на realtime: `supabase.channel('shopping_items').on('postgres_changes', { event: '*', schema: 'public', table: 'shopping_items' }, reload)`. Defensive: ловим 42P01 (таблица не создана) → пустой список, как в `useTransfers`.

- [x] **Фаза 3. Страница `/shopping` + роут + навбар.**
  - `src/pages/Shopping.tsx`:
    - Заголовок «🛒 Покупки».
    - Сверху — `<input>` с placeholder «Добавить позицию...» + кнопка ➕. Enter тоже добавляет. После добавления — фокус остаётся в поле, оно очищается.
    - Paste: `onPaste` ловит текст, если в нём `\n` — split, фильтр пустых, `addBatch`. Иначе обычный paste.
    - Секция «Купить» — список `pending`. Каждая строка: круглый чекбокс (тап → toggle) + title + крестик в правом краю (тап → remove, опционально показать снэкбар «Удалено · Отменить»).
    - Секция «Куплено сегодня» (показывается только если `doneToday.length > 0`): сворачивающийся блок (по умолчанию свёрнут, заголовок «✓ Куплено сегодня · N»). Внутри — те же строки, но title зачёркнутый и серый. Тап по чекбоксу возвращает обратно в pending.
    - Empty state для pending: «Список пуст. Добавьте первую позицию ↑» с лёгкой иллюстрацией (эмодзи).
    - Empty state когда household = 1 человек (партнёр не принял invite): обычный список работает, но мелким текстом «Партнёр пока не присоединился — пригласите в Настройках, чтобы видеть список вместе».
  - Роут `/shopping` в `src/App.tsx` рядом с `/operations`.
  - Пункт «Покупки» в `src/components/AppLayout.tsx` в навбаре. Позиция: между «Операции» и «Календарь»/«Цели» (точно решу при реализации — нужно глянуть текущий порядок). Иконка — 🛒 или SVG cart.

- [ ] **Фаза 4. Виджет на Dashboard (опционально, минимальный).**
  - Маленькая плашка `<ShoppingBadge>` на Dashboard: если `pending.length > 0` → строка «🛒 В списке покупок: **N позиций** →» с ссылкой на `/shopping`. Если ноль → не показывается (не засоряет дашборд).

- [ ] **Фаза 5. UX-проверка + edge cases.**
  - `npm run dev`, обход:
    1. Один партнёр в household → добавил 3 позиции, отметил одну, удалил одну → корректно отображается «1 в списке, 1 куплено сегодня».
    2. Два партнёра (два браузера/инкогнито): A добавил «молоко» → у B появилось в течение секунды без обновления страницы (realtime).
    3. B отметил «молоко» галочкой → у A позиция переехала в «Куплено сегодня».
    4. A вставляет в поле ввода блок текста из 10 строк → 10 позиций добавились одним запросом, у B все 10 пришли realtime'ом.
    5. Очень длинный title (>200 символов) → клиент режет до 200 или показывает hint «слишком длинно», БД-check не падает с 500.
    6. Пустая строка / только пробелы → не добавляется, поле подсвечивается.
    7. На следующий день старые «куплено вчера» позиции автоматически не показываются в `doneToday` (граница по локальному дню). Они остаются в БД с `checked_at` от вчера.
  - Edge cases:
    - Сетевая ошибка при insert → toast «не удалось добавить, проверьте сеть», поле не очищается.
    - RLS-конфликт (мифический: позиция из чужого household) → invisible, falls into 0 rows, не падает.
    - Миграция не применена (`42P01`) → страница рендерит пустое состояние, без ошибки.

## Открытые вопросы

- **Push-уведомление «партнёр добавил позицию»?** Фаза 8 проложила backend для Web Push. Можно повесить trigger на insert в `shopping_items` → notification «Алина добавила в список: молоко». **Решение для MVP: не делаем.** Reasoning: жена будет добавлять 10 позиций подряд — это 10 push'ей подряд, что бесит. Если когда-нибудь захотим — делать с дебаунсом «накопила 5 позиций или прошло 5 минут → один push “обновился список покупок”». Отдельная фича.
- **Подсказки / автодополнение из истории?** «Раньше покупали “молоко 2.7%” → подсказать». Полезно, но добавляет сложность (нужна history-таблица или вычисление distinct по checked items). Отложено — ветка `feat/shopping-suggestions` после месяца использования, когда накопятся данные.
- **Сортировка купленного по магазину / категории?** Нет, MVP — flat-список. Это `feat/shopping-multilists` или `feat/shopping-categories`.
- **Количество / единицы (`2 л молока`)?** Пишется в title. Структурированные поля = отдельная ветка, если выяснится, что нужно для аналитики.
- **Совместимость с офлайн-режимом PWA?** SW настроен для финтрекера. Запись в офлайне → выкатится при появлении сети через стандартный supabase-js retry. Если нет — отдельная ветка `feat/shopping-offline-queue`. Не блокирующее для MVP — оффлайн в магазине Шуферсал маловероятен (там Wi-Fi).
- **Аналитика «что покупаем чаще всего»?** Не в MVP. Данные собираются (deleted_at = null + checked_at history), потом можно сделать report. Это `feat/shopping-stats`.
- **Удаление через свайп vs крестик?** В MVP — крестик. Свайп = ещё один UX-паттерн, который надо учить. Если жена сама попросит свайп — добавим.

## Инварианты

- Список — собственность household, не индивидуальная. RLS по `household_id in (select household_id from members where profile_id = auth.uid())`.
- Никакого `is_private` / приватных позиций. Полный шер внутри пары.
- Удаление — soft (`deleted_at`), не hard. Это даёт «Отменить» в snackbar и сохраняет историю для будущей аналитики.
- Realtime через Supabase publication. Без неё фича теряет половину смысла (асимметрия А-пишет / Б-в-магазине).
- `service_role` не используется (никаких Edge Functions / триггеров для этой фичи).
- `npm run build && npx tsc --noEmit && npm run lint` чистые перед коммитом каждой подфазы.

## Не входит в эту ветку (намеренно)

- **Несколько списков** — `feat/shopping-multilists`.
- **Категории / магазины / приоритеты** — отдельные ветки по необходимости.
- **Push «партнёр добавил позицию»** — `feat/shopping-push` (с дебаунсом).
- **Автосоздание operation из купленного** — `feat/shopping-to-expense`.
- **Подсказки из истории покупок** — `feat/shopping-suggestions`.
- **Аналитика покупок** — `feat/shopping-stats`.
- **Offline-queue для записей без сети** — `feat/shopping-offline-queue`.
- **Голосовой ввод** — отменён глобально (см. [[feedback-no-voice-input]]).
