# План: Фаза 5 — Крипта

Цель ветки `feat/kripta` — закрыть Фазу 5 из ROADMAP. После мержа у каждого супруга появляется **личный** крипто-портфель:

1. Журнал операций (buy / sell / transfer_in / transfer_out / fee / airdrop) по монетам.
2. Авто-цены с CoinGecko раз в час (ILS / USD / EUR), пишутся Edge Function под `pg_cron`.
3. Дашборд портфеля: текущая стоимость в base_currency, allocation (donut), реализованный + нереализованный P&L.
4. Виджет «Крипто-портфель» на главном Dashboard (под подушкой безопасности).
5. Налоговый отчёт по FIFO (Capital Gains, Израиль 25%) + CSV-экспорт для налоговой.

Зафиксировано до старта: **крипта личная у каждого**. RLS отсекает чужие холдинги — партнёр не видит ни мои монеты, ни мои сделки, ни мой tax-отчёт. Это симметрично с personal-счетами фаз 2 и 4.

UX-фильтр Фазы 3-4 («поймёт ли жена с первого раза, без объяснений?») остаётся главным критерием. На странице `/crypto` главная цифра одна — текущая стоимость в шекелях. P&L — мелким серым. FIFO, lots, cost basis — не вылезают наружу нигде кроме страницы налогового отчёта.

> **Расхождение с overview.md**: в `.business/products/overview.md` налоговая отчётность (включая FIFO/Capital Gains) лежит в stop-list. Но ROADMAP (свежее, 2026-05-26) её явно включает — «Уровень 3: подготовка налогового отчёта для Израиля». Считаем ROADMAP актуальной правдой; overview обновлю по итогам ветки.

## Принципы

- **Крипта — личная сущность.** Решение: `crypto_holdings.profile_id NOT NULL` (а не `household_id`). Reasoning: shared-крипта на двоих — это юридическая каша (на чьё имя на бирже, как делить gain'ы в налоговой). Личная зона решает это просто — каждый ведёт свой портфель, налоговая декларация подаётся индивидуально. Если когда-нибудь захочется «общий счёт на криптобирже» — добавим параллельную таблицу `shared_crypto_holdings` отдельной веткой. Сейчас не нужно.
- **Custodian — свободный текст, не справочник.** Bittrex закрылся, Binance Israel ушёл, Trezor — это устройство. Делать enum/справочник бирж — overengineering и поломка через год. `custodian text NOT NULL` + autocomplete по уже введённым значениям в UI. UNIQUE на `(profile_id, coin_id, custodian)` — один и тот же набор «BTC на Binance» не дублируется.
- **Транзакции — append-only journal, баланс выводится агрегацией.** Не храним `crypto_holdings.balance` колонкой. Reasoning: расхождение `balance` и `sum(transactions)` после первого же edit-а — классическая боль. Баланс считаем на клиенте через `currentBalance(transactions)`. Если станет медленно (тысячи сделок) — материализуем view, не раньше.
- **Цена в `price_per_unit_base` — в base_currency семьи, не в монете.** При вводе buy/sell пользователь видит «купил 0.5 BTC за 50 000 ₪» — это естественная фраза для жителя Израиля. Если хранить «цена за 1 BTC в USDT» и потом конвертить — теряем точность и наследуем хвост стейблкоина. Для transfer_in/out цена `nullable` (перевод между своими кошельками — не доход и не расход).
- **CoinGecko — справочные цены, не первоисточник для tax.** Cron подтягивает цены в `crypto_prices` для UI и подсказок («последняя известная цена — 380 000 ₪»). В FIFO-расчёте используется `price_per_unit_base` из самой транзакции (что пользователь вбил, то и есть фактическая цена сделки). Это правильно с точки зрения налоговой: gain = реальная цена продажи − реальная цена покупки, а не «по CoinGecko».
- **FIFO детерминированный.** При одинаковых `occurred_at` сортировка по `created_at asc`. Это критично — налоговый отчёт должен воспроизводиться от запуска к запуску. Tie-break через `id` (uuid) дал бы нестабильность.
- **Всё в `base_currency` семьи.** Текущая стоимость портфеля считается в base. CoinGecko умеет отдавать цену сразу в ILS/USD/EUR — не делаем лишнюю конверсию через USD. Цены тянем во всех трёх валютах, в UI/расчётах берём ту, что совпадает с `households.base_currency`. Если базовая валюта семьи поменялась — берём последнюю доступную, fallback на USD.
- **RLS вместе с CREATE TABLE; GRANT-ы явные.** Тот же урок Фазы 2.10 / 4.1. `service_role` явно гранчуем только на `crypto_prices` (туда пишет Edge Function fetch-coingecko-prices). На `holdings`/`transactions` — только authenticated, и строго `profile_id = auth.uid()`. Партнёр не «видит чуть-чуть» — он не видит ничего.
- **Графики — inline SVG, как в Фазе 3.** Donut allocation — тот же приём, что в `CategoryBreakdown`. Никаких chart-библиотек.
- **UX-фильтр на странице:**
  ```
  💰 24 740 ₪          ← общая стоимость портфеля, крупно
  📈 +3 120 ₪ (+14%)   ← P&L (realized + unrealized) одной строкой, мелким серым

  ┌─────────────────────────────────────┐
  │ ₿ BTC      0.0234   18 200 ₪   73%  │
  │ Ξ ETH      1.50      5 240 ₪   21%  │
  │ ◎ SOL      45.0      1 300 ₪    5%  │
  └─────────────────────────────────────┘
  ```
  Custodian показываем мелким серым во второй строке («Binance», «Trezor»). Никаких «cost basis», «realized vs unrealized» отдельно — это страница tax. На главной /crypto одна цифра ценнее трёх правильных.
- **Build + tsc + lint чистые** перед коммитом каждой подфазы (как в Фазах 3-4).

- [x] **Фаза 5.4. Чистые агрегаты `src/lib/crypto.ts`.**
  - `currentBalance(transactions): number` — сумма `amount` по знаку:
    - `buy`, `transfer_in`, `airdrop` → `+amount`
    - `sell`, `transfer_out`, `fee` → `−amount`
    - Один проход, O(n). Возвращает в монете.
  - `currentValue(balance, lastPriceInBase): number` — `balance * lastPriceInBase`. Возвращает в `base_currency`.
  - `fifoCostBasis(transactions): { realizedPnl: number; remainingLots: Lot[]; soldLots: Sale[] }`:
    - `Lot = { acquiredAt: Date; amount: number; pricePerUnitBase: number; txId: string }`.
    - `Sale = { soldAt: Date; soldAmount: number; salePricePerUnit: number; matchedLots: { lotTxId: string; amountUsed: number; pricePerUnit: number }[]; gain: number }`.
    - Алгоритм: сортируем transactions по `(occurred_at asc, created_at asc)`. Идём один проход:
      - `buy` или `airdrop` (с `price_per_unit_base != null`) → push в очередь лотов. Для `airdrop` без цены — цена 0 (получено бесплатно, налоговая база нулевая; gain при продаже = весь proceeds). Для `transfer_in` без цены — НЕ создаёт лот (это не приобретение, это перемещение между моими кошельками; FIFO для tax считает только приобретения «снаружи»). _Тонкость: если перевёл с биржи на холодник, я не «купил» — лот в FIFO уже есть с момента buy. Поэтому правильнее: transfer_in/out FIFO не трогают._
      - `sell` → жрём лоты с головы очереди (FIFO), пока не наберём нужный `amount`. Для каждого «откушенного куска лота» считаем `gain = (sellPrice − lotPrice) * amountUsed`. Накопительно складываем в `realizedPnl`. Складываем Sale-запись для tax-отчёта (там надо «дата покупки лота / дата продажи / amount / cost basis / proceeds / gain»).
      - `transfer_in`, `transfer_out` — пропускаем (не влияют на FIFO, влияют только на `currentBalance`).
      - `fee` — пропускаем для FIFO (комиссии можно учитывать в gain, но это сложнее и спорно для tax; берём fee отдельно). _Решение: пока fee не учитываем в gain. Позже при необходимости добавим `fee_base / 2 → buy-side, fee_base / 2 → sell-side`._
    - **Sell больше, чем есть лотов** → используем что есть (gain = весь proceeds), и кидаем warning через возвращаемый флаг `inconsistent: true`. UI пометит «недостаточно лотов» — это значит, пользователь забыл ввести `airdrop`/`transfer_in` с покупкой.
    - **Tie-break при одинаковом `occurred_at`** → по `created_at asc`. Если и тот совпадает (что почти невозможно с timestamp с микросекундами) — по `id asc`. Гарантирует детерминированность.
    - **Возвращаем sortedTransactions** ради того, чтобы UI мог отобразить ту же самую сортировку, что в FIFO. Это важно для проверки руками («посмотри, вот в этом порядке оно их жрёт»).
  - `unrealizedPnl(remainingLots, lastPriceInBase): number` — для каждого остающегося лота: `(lastPrice − lotPrice) * lotAmount`. Сумма.
  - `portfolioAllocation(holdings, balancesByHolding, pricesByCoinId): { coinId: string; symbol: string; valueBase: number; share: number }[]`:
    - Группируем holdings по `coin_id` (один coin может быть на нескольких биржах — суммируем).
    - Для каждой группы: `valueBase = totalBalance * lastPrice`.
    - `share = valueBase / totalPortfolioValue` (0..1).
    - Сортировка по `valueBase desc`. Монеты с `valueBase = 0` (всё продано или пыль) — фильтруем `< 0.01`.
  - `taxReportFor(year, transactions): { sales: Sale[]; totalGain: number; taxAmount: number }`:
    - Фильтр `sell` с `occurred_at` в указанном году. Для каждого sell — берём данные из `fifoCostBasis(allTransactions).soldLots` (нужны все транзакции, не только за год, иначе FIFO начнёт «с воздуха»).
    - `totalGain = sum(sale.gain)` (может быть отрицательным — убыток).
    - `taxAmount = max(totalGain, 0) * 0.25`. _Замечание: в Израиле убытки можно переносить, но это пользователь решает в декларации — мы цифру убытка показываем, а налог считаем только с положительной прибыли. Это базовый MVP-уровень._
  - Юнит-тестов нет (как и в Фазах 3-4), но в комментариях фиксируем 2-3 примера ввод/вывод:
    - Кейс из задания: buy 1 BTC по 100 000, buy 1 BTC по 120 000, sell 1.5 BTC по 150 000 → cost basis = 100 000 + 0.5×120 000 = 160 000; proceeds = 1.5×150 000 = 225 000; gain = 65 000; tax = 16 250 ₪. Remaining lots = 0.5 BTC по 120 000.

## Открытые вопросы

- **Хранить ли исторические цены CoinGecko для P&L-графика «как менялась стоимость портфеля»?** Да — `crypto_prices` уже append-only с `as_of`. График «портфель за месяц» — отдельная маленькая фича, можно отложить на Фазу 8/полировку. В MVP только «сейчас vs cost basis».
- **Что делать со stable-coin'ами (USDT/USDC) в P&L?** USDT можно «купить за 1 ₪ × 3.7» — цена практически не двигается, gain околонулевой. Это окей. Главное, что в портфеле они отображаются. Если когда-нибудь захочется «исключить стейблы из P&L» — флаг в `cryptocurrencies.is_stablecoin` и фильтр в `unrealizedPnl`. Не в MVP.
- **Учитывать ли комиссию в cost basis (для уменьшения налога)?** Можно: `cost = price + fee_attributed`. Это легитимно по израильскому tax-law. Но усложняет FIFO. **Решение для MVP**: показываем `fee_base` в транзакциях, но в gain не учитываем — это занижает gain (то есть налог консервативно завышен, что лучше, чем недоплатить). Для второй итерации Фазы 5 — учесть.
- **Что если CoinGecko добавит новую монету, которой у нас нет в `cryptocurrencies`?** Пользователь захочет купить SUI / TON / DOGE → мы пока не поддерживаем. Решение: добавление новой монеты — отдельная мини-миграция (`20260601_add_coins.sql`). Это редко, контролируемо.
- **Multi-portfolio через `custodian` или через `crypto_accounts` (новая таблица)?** Сейчас выбран custodian-как-текст. Альтернатива: завести `crypto_accounts (id, profile_id, name, kind)` и привязывать holdings к нему. Это даст «портфель Binance» как сущность. **Решение**: пока не нужно — custodian-текст покрывает 90%. Если потом захочется «суммарный P&L по Binance vs Trezor» — миграция custodian → FK на crypto_accounts.
- **Налоговая ставка в Израиле — всегда 25%?** Сейчас для физлиц на крипту — да (Capital Gains Tax 25%). Но для day-trader'ов и больших оборотов налоговая может приравнять к бизнес-доходу (до 50%). В MVP считаем 25%, в UI можем потом добавить переключатель ставки. Не в этой ветке.
- **«Шорт-позиции», «стейкинг», «свопы», «liquidity pools»** — всё это сложные кейсы. **Не в MVP.** Перечислены в «Не входит».
- **Реалтайм-обновление цен на странице `/crypto`** — websocket или polling? **Решение**: 60-секундный setInterval — простой, надёжный, не требует Realtime от Supabase. Цены меняются медленнее минуты, пользователю хватит.

## Инварианты

- **Личная приватность абсолютная**. RLS строго `profile_id = auth.uid()` на holdings; для transactions — через EXISTS на holdings. Партнёр не видит ни одного холдинга, ни одной транзакции, ни одной строки tax-отчёта. Проверяется в фазе 5.8 двумя аккаунтами.
- **Стоимость портфеля — в base_currency семьи** через `useCryptoPrices(base)`. CoinGecko отдаёт в ILS/USD/EUR — лишняя конверсия не нужна.
- **Цена сделки — в base_currency**, не в монете и не в USDT. Это устраняет необходимость в курсах валют на дату сделки для FIFO.
- **RLS вместе с CREATE TABLE; GRANT-ы явные**. `service_role` гранчуется только на `crypto_prices` (+ select на `cryptocurrencies`). На `holdings`/`transactions` service_role не нужен — Edge Function в них не пишет.
- **FIFO детерминированный**: sort by `(occurred_at asc, created_at asc, id asc)`. Воспроизводимость tax-отчёта от запуска к запуску — must have.
- **Append-only journal**. Баланс холдинга = `currentBalance(transactions)`, не отдельная колонка. Никаких «балансов в БД, которые могут разъехаться с историей».
- **CoinGecko-цены — справочные**, не используются в FIFO. FIFO смотрит только в `price_per_unit_base` транзакций. Это правильно для tax: gain = фактическая сделка − фактическая покупка.
- **Графики — inline SVG**, как в Фазе 3.
- **UX-фильтр на `/crypto`**: одна главная цифра — стоимость в шекелях. P&L и allocation — поддерживающие. На `/crypto/tax` UX сложнее, но эта страница не для жены, а для подачи декларации.
- **`npm run build && npx tsc --noEmit && npm run lint`** чистые перед коммитом каждой подфазы.

## Не входит в эту ветку (намеренно)

- **Стейкинг / yield / DeFi-протоколы** — отдельная Фаза («крипто-инвест-доход»).
- **Свопы между монетами (BTC → ETH через 1inch)** — пока приравниваем к `sell BTC + buy ETH` двумя ручными транзакциями. UI-ассистент «своп одним диалогом» — отдельная мини-фича.
- **Liquidity pools / LP-токены** — не MVP.
- **Шорт-позиции / margin / фьючерсы** — не MVP, и в принципе вне scope продукта.
- **NFT** — не MVP, и пока вообще не на радаре.
- **Авто-импорт из Binance API / Trezor Suite** — отдельная Фаза («импорт из бирж»). Сейчас всё руками.
- **Реалтайм через Supabase Realtime** — 60-сек polling достаточно.
- **График стоимости портфеля во времени** — данные есть в `crypto_prices`, но рисование — отложено на полировку.
- **Учёт комиссии в cost basis** — пока fee хранится, но в gain не входит (см. Открытые вопросы).
- **Переключатель налоговой ставки** (для day-trader'ов 50%) — пока хардкод 25%.
- **Multi-currency tax-отчёт** (если базовая валюта семьи поменялась на USD в середине года) — отдельная боль, отложено.
- **Шифрование данных на клиенте** (zero-knowledge) — RLS достаточно для семьи из двоих. Если когда-нибудь возьмёт страх «Supabase admin прочтёт мои сделки» — отдельная архитектурная ветка.

## Итог

Реализовано в ветке `feat/kripta`:

**Схема БД (2 миграции, applied to prod):**
- `20260530300000_crypto_core.sql`: `cryptocurrencies` (seed BTC/ETH/USDT/USDC/SOL, поля `coingecko_id`, `decimals`, `icon`, `is_active`), `crypto_holdings` (личные через `profile_id NOT NULL`, UNIQUE `(profile_id, coin_id, custodian)`), `crypto_transactions` (append-only, kind enum из 6 значений, CHECK для buy/sell требует `price_per_unit_base`, индекс `(holding_id, occurred_at, created_at)` для FIFO-сортировки), `crypto_prices` (UNIQUE `(coin_id, quote_code, as_of)`, last-price-индекс). RLS строго `profile_id = auth.uid()` на holdings + EXISTS на transactions. GRANT-ы явные: authenticated CRUD на holdings/transactions, service_role write на crypto_prices.
- `20260530300100_fetch_coingecko_prices_cron.sql`: pg_cron job `fetch_coingecko_prices_hourly` на `5 * * * *` через pg_net (тот же паттерн, что `fetch_ecb_rates_daily`). Идемпотентность через cron.unschedule.

**Edge Function:**
- `supabase/functions/fetch-coingecko-prices/index.ts`: тянет CoinGecko `simple/price` для всех активных монет в ILS/USD/EUR, апсёртит в `crypto_prices` по `(coin_id, quote_code, as_of)`. `as_of` округляется до начала часа в UTC → повторный вызов внутри часа не плодит строк. **Не задеплоена** — нужен PAT (см. ниже).

**Чистые агрегаты (`src/lib/crypto.ts`):**
- `currentBalance(transactions)` — сумма по знакам.
- `currentValue(balance, lastPrice)` — стоимость в base; null при отсутствии цены.
- `fifoCostBasis(transactions)` — детерминированный FIFO по `(occurred_at, created_at, id)`. buy/airdrop создают лот; sell съедает с головы; transfer_in/out и fee FIFO не трогают. Возвращает `realizedPnl`, `remainingLots`, `soldLots` (для tax-таблицы), `inconsistent` (sell без лотов).
- `unrealizedPnl(remainingLots, lastPrice)` — null при отсутствии цены.
- `portfolioAllocation(holdings, txByHolding, prices, coins)` — группировка по `coin_id`, отсечка пыли < 0.01.
- `taxReportFor(year, transactions)` — фильтр SoldLot по году продажи, `totalGain`/`totalLoss`/`netGain`/`taxAmount` (25%).
- `groupByHolding(transactions)` — helper.

**Проверено вручную через node `--experimental-strip-types`:**
- Кейс плана (buy 1@100k, buy 1@120k, sell 1.5@150k) → realizedPnl 65 000, soldLots gains [50 000, 15 000], remainingLots [{0.5 @ 120k}], taxAmount **16 250 ✓**.
- Кейс 0.5+0.5 BTC по 350k и 420k, sell 0.7@450k → netGain 56 000, remaining [{0.3 @ 420k}], taxAmount **14 000 ✓**.
- Airdrop 100 @ null + sell 50 @ 5 → netGain 250 (весь proceeds), taxAmount **62.5 ✓**.
- Transfer_in/out нейтральны: buy 1@100, transfer_out 0.5, transfer_in 0.5, sell 1@200 → netGain **100, tax 25 ✓**.

**Хуки:**
- `useCryptoCoins` — справочник, defensive 42P01.
- `useCryptoHoldings` — list/create/remove; UNIQUE-conflict возвращает существующий.
- `useCryptoTransactions(holdingId?)` — list/create/update/remove; сортировка `(occurred_at, created_at)` совпадает с FIFO.
- `useCryptoPrices(quote='ILS')` — последняя цена per coin за 24ч, refresh каждые 60с через setInterval.
- CustomEvents `ff:crypto-{holdings,transactions}-changed` для перекрёстной реактивности (Dashboard + /crypto).

**UI:**
- **`/crypto`:** шапка (стоимость + P&L + %), SVG-donut allocation, список `<CryptoHoldingCard>`, кнопки «+ Холдинг» и «+ Операция», лента транзакций desc по дате, ссылка «Налоговый отчёт →».
- **`<CryptoHoldingCard>`:** иконка монеты, custodian мелким серым, balance с `decimals`-trim, value крупно, P&L с подсветкой, кнопка «+ Операция», «Удалить» только для пустых.
- **`<CryptoDonut>`:** generic SVG donut с фиксированной палитрой по индексу, hover-dimming сегментов (тот же приём, что в `CategoryBreakdown`).
- **`<NewHoldingDialog>`:** select монеты + custodian-text с `<datalist>` из существующих значений профиля.

- **`/crypto/tax`:** select года + 3 плашки (gain/loss/налог) + полная таблица sell-сделок с разбивкой по лотам FIFO, итог net gain + tax. Кнопка «Экспорт CSV» (8 колонок, UTF-8 BOM для Excel). Свёртка «По годам» — sum-сводка. Баннер при FIFO inconsistent.

Из косяков по ходу: `Crypto.tsx` сначала падал на `react-hooks/rules-of-hooks` (useMemo после `if (!household) return null`) — перетащил memo выше early return; `crypto.ts` ESLint ругался на `no-useless-assignment` для `remaining = 0` перед `break` — убрал.

**Деплой:**
- Миграции применены к prod через `npm run db:push` (две операции, без интерактива).
- Cron-задача `fetch_coingecko_prices_hourly` стоит в pg_cron, **но функция fetch-coingecko-prices не задеплоена** в Supabase — нужен `SUPABASE_ACCESS_TOKEN`. См. промт для Клода-с-браузером в секции «Деплой Edge Function» выше. До деплоя функции `crypto_prices` будет пустым, UI отрисует «P&L: цены ещё не подтянулись» и портфель без текущей стоимости. Транзакции, FIFO и tax-отчёт работают без цен.

**Что осталось за пределами ветки (как запланировано):**
- Интерактивный браузерный обход с реальными данными — `npm run dev` поднимался, `/`, `/crypto`, `/crypto/tax` отдают 200, все новые модули трансформируются Vite без ошибок. Ручной кликовый сценарий «холдинг → операция → виджет обновился» в этой сессии не выполнялся. Edge cases покрыты статически:
  - 0 холдингов → виджет на Dashboard null, `/crypto` empty-state.
  - Цены нет → currentValue/unrealizedPnl = null, UI «—» и «цены ещё не подтянулись».
  - sell > buy → FIFO inconsistent, баннер на tax.
  - airdrop без цены → лот с cost 0, gain = весь proceeds.
  - transfer_in/out → не трогают FIFO; balance меняется.
  - партнёр (другой profile_id) → ноль строк через RLS.
- Дeплой Edge Function — после получения PAT.
- Учёт комиссии в cost basis, стейкинг, NFT, шорт, реалтайм-обновление через Supabase Realtime, график стоимости портфеля во времени — отложено (см. «Не входит в эту ветку»).
