# План: Фаза 2 — Базовый учёт операций (счета + категории + операции)

Цель ветки — закрыть Фазу 2 из ROADMAP **целиком**: счета, категории, операции, переводы между счетами, регулярные операции и мультивалюта (с подтягиванием курсов из ECB). С первого дня — двухуровневая приватность (visibility у счёта, is_private у операции) и RLS.

После этой ветки пара сможет вести полноценный учёт включая разные валюты и автозалив зарплаты. Аналитика, бюджеты, цели — Фаза 3+.

## Принципы

- **Один план = одна функция** (правило `CLAUDE.md`). Функция здесь = «учёт операций».
- **Слоями.** Сначала core (счета/категории/операции) → потом переводы → потом регулярки → потом мультивалюта. Не наоборот — каждый следующий слой опирается на предыдущий и тестируется отдельно.
- **RLS с первого дня**, в той же миграции, что и таблица.
- **Двухуровневая приватность** из памяти проекта. Поля сразу: `accounts.visibility ∈ {personal, shared}`, `operations.is_private boolean`. Логика: partner не видит ни `personal` счёт супруги, ни её операций с `is_private=true` на shared-счёте.
- **Валюта по умолчанию ILS**, но архитектурно — мультивалютно. Каждый счёт со своей валютой, операции в валюте счёта. На дашборде агрегируем в одну («base currency» семьи, default ILS) через snapshot курса на дату операции.
- Никаких UI-библиотек поверх Tailwind. Формы — нативные `<input>` и наши `AuthInput`/`PrimaryButton` из Фазы 1.

## Фазы

  - Миграция `XXXX_operations_core.sql`:
    - `accounts` (id uuid, household_id, owner_profile_id, name, currency='ILS', visibility check `personal|shared`, initial_balance numeric(14,2) default 0, created_at).
    - `categories` (id uuid, household_id, name, kind check `expense|income`, icon text nullable, color text nullable, is_default bool, created_at). Семейные, без visibility — у пары один справочник на двоих.
    - `operations` (id uuid, household_id, account_id, category_id, author_profile_id, kind check `expense|income`, amount numeric(14,2) > 0, occurred_at date, note text nullable, is_private bool default false, created_at).
    - Все 3 таблицы — `enable row level security` + GRANT для `authenticated` (помним урок Фазы 1).
    - Полезные индексы: `operations(household_id, occurred_at desc)`, `operations(account_id)`.

- [x] **Фаза 2.2. RLS-политики двухуровневой приватности.**
  - `accounts`:
    - SELECT — если ты член household И (visibility='shared' ИЛИ owner_profile_id = auth.uid()).
    - INSERT/UPDATE/DELETE — только owner_profile_id = auth.uid().
  - `categories`:
    - SELECT/INSERT/UPDATE/DELETE — членам household (общий справочник).
  - `operations`:
    - SELECT — если ты член household И счёт под этой операцией тебе виден (см. accounts policy) И (is_private=false ИЛИ author_profile_id = auth.uid()).
    - INSERT — author_profile_id = auth.uid() И счёт тебе виден (на свой personal или на любой shared household).
    - UPDATE/DELETE — только author_profile_id = auth.uid() (пока без admin-кейса).
  - Помним: INSERT с RETURNING требует, чтобы вставленная строка проходила SELECT. Проверяем мысленно для каждой политики.

## Итог

Реализовано в ветке `feat/operatsii-i-scheta`:

- **Схема (миграции 20260527193923–201655):** `accounts`, `categories`, `operations`, `transfers`, `operation_schedules` — все 5 таблиц с RLS «с первого дня» и явными GRANT-ами для `authenticated`.
- **Двухуровневая приватность:** `accounts.visibility ∈ {personal,shared}` + `operations.is_private boolean` — реализована и проверена через RLS-симуляцию двух профилей (Ави owner, Алина partner). Алина не видит ни personal-счёт Ави, ни приватные операции на shared-счёте, ни возможности редактировать/удалять чужое.
- **Дефолтные категории** под Израиль: 14 expense + 4 income, посеяны автоматически при создании семьи через `seed_default_categories()`.
- **UI:**
  - `/settings` → Accounts (CRUD счетов с radio personal/shared).
  - FAB «+» с модалом `AddOperationDialog` — три таба: расход / доход / перевод; toggle приватности появляется только для shared-счёта.
  - `/operations` — список с фильтром по периоду, группировкой переводов в одну строку «↔», респектом `viewMode` (личное / семейное).
  - `Dashboard` — Баланс, итоги месяца (income/expense/net, переводы исключены), список счетов с балансами, карточка «Ближайшие списания за 7 дней».
- **Переводы (`transfers`):** RPC `create_transfer` атомарно пишет 1 transfer + 2 операции с одинаковым `transfer_id`. FK `operations.transfer_id REFERENCES transfers(id) ON DELETE CASCADE` → удаление transfer удаляет обе ноги.
- **Регулярные операции (`operation_schedules`):** ежедневный pg_cron-таск дёргает `tick_schedules()` → создаёт операцию + сдвигает `next_run_at` по `cadence_rule` (`monthly:N` и `weekly:<dow>`).
- **Мультивалюта (Фаза 2.10)** — намеренно вынесена в отдельную ветку `feat/multivalyuta` (см. `plans/2026-05-27-multivalyuta.md`), чтобы поскорее замержить устойчивый core Фазы 2 в `main`. Все таблицы Фазы 2 уже хранят `currency` (default `'ILS'`); добавление справочников `currencies`/`fx_rates` и Edge Function `fetch-ecb-rates` ничего не ломает.

Сценарии 2.11 A–G пройдены через симуляцию RLS под `set request.jwt.claims` + code review UI. Сценарий H перенесён в ветку мультивалюты.
