# План: Фаза 2 — Базовый учёт операций (счета + категории + операции)

Цель ветки — превратить «вход в продукт» из Фазы 1 в реально работающий финтрекер: пользователь может завести счёт, добавить трату или доход, увидеть список операций и баланс. С первого дня — двухуровневая приватность (visibility у счёта, is_private у операции) и RLS.

После этой ветки пара сможет начать вести реальный учёт. Анализ, бюджеты, цели — Фаза 3+.

## Принципы

- **Один план = одна функция** (правило `CLAUDE.md`). Функция здесь = «учёт операций».
- **Узкое русло сначала.** Не пытаемся закрыть весь Фаза-2-список ROADMAP в одной ветке. Сначала самое узкое работающее русло: счёт → операция → список → баланс. Мультивалюту, переводы и регулярные — отдельной веткой.
- **RLS с первого дня**, в той же миграции, что и таблица.
- **Двухуровневая приватность** из памяти проекта. Поля сразу: `accounts.visibility ∈ {personal, shared}`, `operations.is_private boolean`. Логика: partner не видит ни `personal` счёт супруги, ни её операций с `is_private=true` на shared-счёте.
- **Валюта пока одна — ILS.** Поле `currency` в `accounts` уже закладываем (`text default 'ILS'`), но в этой ветке UI не предлагает выбор. Мультивалюту прикрутим следующей веткой.
- Никаких UI-библиотек поверх Tailwind. Формы — нативные `<input>` и наши `AuthInput`/`PrimaryButton` из Фазы 1.

## Фазы

- [ ] **Фаза 2.1. Схема БД — accounts, categories, operations + RLS + GRANT.**
  - Миграция `XXXX_operations_core.sql`:
    - `accounts` (id uuid, household_id, owner_profile_id, name, currency='ILS', visibility check `personal|shared`, initial_balance numeric(14,2) default 0, created_at).
    - `categories` (id uuid, household_id, name, kind check `expense|income`, icon text nullable, color text nullable, is_default bool, created_at). Семейные, без visibility — у пары один справочник на двоих.
    - `operations` (id uuid, household_id, account_id, category_id, author_profile_id, kind check `expense|income`, amount numeric(14,2) > 0, occurred_at date, note text nullable, is_private bool default false, created_at).
    - Все 3 таблицы — `enable row level security` + GRANT для `authenticated` (помним урок Фазы 1).
    - Полезные индексы: `operations(household_id, occurred_at desc)`, `operations(account_id)`.

- [ ] **Фаза 2.2. RLS-политики двухуровневой приватности.**
  - `accounts`:
    - SELECT — если ты член household И (visibility='shared' ИЛИ owner_profile_id = auth.uid()).
    - INSERT/UPDATE/DELETE — только owner_profile_id = auth.uid().
  - `categories`:
    - SELECT/INSERT/UPDATE/DELETE — членам household (общий справочник).
  - `operations`:
    - SELECT — если ты член household И счёт под этой операцией тебе виден (см. accounts policy) И (is_private=false ИЛИ author_profile_id = auth.uid()).
    - INSERT — author_profile_id = auth.uid() И счёт тебе виден (на свой personal или на любой shared household).
    - UPDATE/DELETE — только author_profile_id = auth.uid() (пока без admin-кейса).
  - Помним: INSERT с RETURNING требует, чтобы вставленная строка проходила SELECT. Проверяем мысленно для каждой политики.

- [ ] **Фаза 2.3. Дефолтные категории под Израиль.**
  - RPC `seed_default_categories(target_household_id uuid) returns void`, SECURITY DEFINER.
  - Список расходов (примерно): «Продукты», «Кафе и рестораны», «Транспорт», «Жильё (арнона, ваад)», «Коммуналка», «Купат-холим», «Связь и интернет», «Одежда», «Развлечения», «Здоровье», «Образование», «Подарки», «Прочее».
  - Список доходов: «Зарплата», «Фриланс/Бонус», «Подарки/Возвраты», «Прочее».
  - Вызывать автоматически при создании household (после INSERT в `households` и `household_members(owner)`). Либо триггером, либо явным вызовом из клиента — решим по ходу (триггер чище).

- [ ] **Фаза 2.4. UI: счета (Settings → Accounts).**
  - Раздел на `/settings`: список существующих счетов, кнопка «Добавить счёт».
  - Форма счёта: имя, тип (personal / shared) — radio, начальный баланс (необязательно, default 0).
  - Тонкое UX-правило: первый счёт после создания семьи добавляется обязательно (онбординг не считается завершённым без счёта? — нет, не блокируем, но Dashboard будет подсказывать).

- [ ] **Фаза 2.5. UI: добавление операции (FAB / большая кнопка).**
  - Большая кнопка «+ Добавить» (в шапке или плавающая внизу).
  - Модал/страница с быстрой формой:
    - Тип: расход / доход (toggle).
    - Сумма (числовой инпут, фокус сразу).
    - Категория (select из categories того же kind).
    - Счёт (select из accounts которые видны юзеру).
    - Дата (default — сегодня).
    - Заметка (необязательно).
    - Приватность (toggle «🔒 не показывать партнёру») — виден только если выбран shared-счёт.
  - После сохранения — обновление списка, тост «Операция добавлена».

- [ ] **Фаза 2.6. UI: список операций (`/operations`).**
  - Заменить заглушку из Фазы 1 на реальный список.
  - Сортировка по `occurred_at desc, created_at desc`.
  - Фильтр по периоду: текущий месяц / прошлый месяц / 7 дней / всё.

## Открытые вопросы (не блокеры)

- Где лучше «+ Добавить» — FAB внизу справа (как в банках) или большая кнопка в шапке? Решу по ходу UI-фазы, посмотрю что меньше клика.
- Удаление счёта с операциями — каскадно или запрещать? Думаю: запрещать (отвечать ошибкой «у счёта есть операции, сначала перенесите/удалите их»). Это аккуратнее.
- Округление сумм — пока `numeric(14,2)`. Этого хватит на сотни тысяч шекелей с копейками. Для крипты в Фазе 5 нужна другая точность.

## Не входит в эту ветку (намеренно — следующие итерации)

- **Мультивалюта** (`currencies`, daily rates через ECB API). Заложили поле `currency` в `accounts`, но UI не предлагает выбор. Всё в ILS.
- **Переводы между счетами** (`transfers`). Пока — добавляешь два встречных «операции».
- **Регулярные операции** (`pg_cron` / приложение). Пока вручную каждый месяц.
- **Бюджеты по категориям**, **аналитика по периодам**, **сравнение месяцев** — это Фаза 3.
- **Импорт CSV из банков**, **фото чека**, **голос** — Фазы 6-8.
