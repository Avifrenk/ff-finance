# План: Фаза 7 — Долги между супругами

Цель ветки `feat/dolgi` — закрыть Фазу 7 из ROADMAP. После мержа пара видит:

1. «Кто кому сколько должен» — одна понятная фраза на Dashboard и на отдельной странице `/debts`.
2. История всех settlement'ов (переводов «в счёт долга»).
3. Кнопка «Погасить долг» — один клик создаёт transfer между personal-счетами супругов с пометкой `is_debt_settlement=true`.

UX-фильтр предыдущих фаз остаётся: на Dashboard жена видит **одну** фразу — «Боб должен Алисе 320 ₪» или «у вас всё ровно». Если кому-то интересны детали — клик ведёт на `/debts`.

## Принципы

- **«Общая трата» = expense на shared-счёте, не приватный, не transfer.** Reasoning: личные операции (personal-счёт ИЛИ `is_private=true`) — это деньги одного человека, к долгам не относятся. Переводы между счетами (`transfer_id != null`) — это не траты, это движение денег по своим карманам. Income на shared-счетах не учитывается: «семья получила зарплату» — это общая копилка, а не долг между супругами.
- **Split 50/50.** Каждая общая трата делится поровну между всеми членами household. Если в семье двое — каждый «должен» по 50% от суммы. Если когда-нибудь будут дети с отдельным аккаунтом — пересчёт пойдёт по числу `members.role in ('owner','partner')` (детей-members у нас не будет, см. overview). Альтернативу «split по пропорции дохода» можно сделать отдельной веткой `feat/debt-split-modes` — не в MVP.
- **Settlement — это transfer с явным флагом.** Решение: добавляем `transfers.is_debt_settlement boolean default false`. Создаётся через RPC `create_transfer` с новым параметром (DROP+CREATE, обратная совместимость через default). Reasoning: альтернативы (магическое слово в `note`, отдельная таблица `debt_settlements`) либо хрупкие, либо переусложнение — для одной строки логики «вычесть из накопленного долга» хватает колонки.
- **Все цифры в `base_currency`.** Конверсия через `convertMoney` (на клиенте) или `convert_to_base()` (на сервере, если когда-нибудь понадобится). Если курс на дату операции отсутствует — она пропускается с пометкой «N операций не учтено». Тот же приём, что в SafetyCushion.
- **Долг — детерминированная функция от operations + transfers + members.** Никаких накопителей в БД, никакого `debts.balance` колонкой. Считается на клиенте за один проход в `lib/debts.ts`. Если станет медленно (тысячи операций) — материализуем view, не раньше.
- **Двухуровневая приватность.** Партнёр всё равно НЕ видит мои `is_private=true` операции через RLS. Значит долг с его стороны и с моей стороны может быть **разный**: я вижу больше операций (свои приватные тоже), он — меньше. Это особенность системы; в UI каждый видит свою цифру долга. Это согласуется с подушкой и балансами Фазы 3-4.
- **Settlement не «переписывает» долг.** Долг считается «накопленный» = `общие траты автор A − общие траты автор B − settlements от A к B + settlements от B к A`, делёное на 2. Так что после settlement цифра «текущий долг» сама уйдёт в 0 (или ближе к нему). Никаких отдельных recalculation'ов не делаем.
- **UI-фильтр на Dashboard:** одна фраза, крупно. Без таблиц, без графиков. На `/debts` уже можно показать детали.
- **Build + tsc + lint чистые** перед коммитом каждой подфазы.

## Открытые вопросы

- **Settlement в кросс-валютной паре?** Если Алиса должна Бобу 500 ₪, но переводит ему 130 $, valid ли это? Решение: использовать существующую логику `create_transfer(p_to_amount)` — фактически зачисленная сумма указывается отдельно, конверсия 500 ₪ → 130 $ остаётся на пользователе. В `computeDebtBalances` для settlement берём `transfers.amount` (сумма списания с from-счёта, в его валюте) и конвертим в base. Симметрично для входящей стороны: берём фактическую сумму на to-счёте (через `operations` с этим `transfer_id` и `kind='income'`). Чтобы не усложнять MVP — пока считаем по `transfers.amount` от обеих сторон с конверсией через fx. Если станет неточно — отдельная итерация.
- **Что если у партнёра вообще нет personal-счёта?** В диалоге settlement — баннер «Создайте personal-счёт». В реальности у каждого партнёра должен быть хотя бы один personal-счёт (это вытекает из дизайна Фазы 2), но MVP-проверка не помешает.
- **Удаление settlement'а?** Через обычный `transfers.delete` (RLS уже разрешает удалять свои/в своей household). Каскадом удалятся 2 operations. Долг пересчитается. ОК.
- **Splits по категориям?** «За еду — 50/50, за арнону — 70/30 (один из партнёров в декрете)». Это **отдельная фича** `feat/debt-custom-splits`, не в MVP. В MVP — strict 50/50.
- **Несколько партнёров (когда-нибудь дети)?** Сейчас considered: ровно 2 owner+partner. Дети-юзеры в продукт не запланированы (см. overview.md). Если когда-нибудь понадобится — переписать `summarizeDebts` для N участников.
- **Долг и крипта?** Крипта личная (Фаза 5), партнёр её не видит. Долги к крипте не относятся.
- **Что считать «sharing» при кросс-валютных операциях?** Если Алиса с shared-EUR счёта потратила 100€, это эквивалент ~400₪. Берём её 400₪ как «общую трату», делим 50/50, Боб должен 200₪. ОК, тот же механизм.

## Инварианты

- Долг — детерминированная функция от operations + transfers + members. Никаких накопителей в БД.
- Только expense на shared-счёте, `is_private=false`, `transfer_id is null` → влияет на долг.
- Settlement → transfer между personal-счетами разных партнёров с `is_debt_settlement=true`. Любой transfer вне этой конфигурации settlement'ом не считается.
- Все расчёты в `base_currency` семьи через `convertMoney`. Курсов нет → операция пропускается, флаг `missingRate`.
- Двухуровневая приватность: каждый пользователь видит **свой** долг (его приватные операции учитываются у него, у партнёра нет).
- RLS на transfers и operations уже настроена в Фазах 2.8 / 2.10 — новой RLS не нужно.
- Только нового SQL — одна колонка + одна DROP+CREATE функция. service_role не трогаем.
- `npm run build && npx tsc --noEmit && npm run lint` чистые перед коммитом каждой подфазы.

## Не входит в эту ветку (намеренно)

- **Custom splits по категориям** — `feat/debt-custom-splits`.
- **Splits по пропорции дохода** — `feat/debt-income-proportional`.
- **Долг автоматически переводится по расписанию** — не нужно, settlement — это явное действие.
- **Уведомления «долг превысил 1000 ₪»** — Web Push (Фаза 8).
- **«Виртуальный» долг без перевода** (когда люди договорились «забыли» долг) — это не наша задача, просто пользователь не создаёт settlement.
- **График динамики долга во времени** — не MVP.
- **Долги с третьими лицами** (друзья, родители) — не наш продукт.
